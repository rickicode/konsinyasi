# Report Specification

> Generated by openlore v1.0.0 on 2026-07-26 01:44
> Source files: src/shared/schemas/report.schema.ts

## Purpose

Manages the asynchronous state of report data, coordinating between UI-driven filter state and the
reports repository to fetch and refresh report summaries with breakdowns.

## Entities

### ReportResponse

> `src/shared/schemas/report.schema.ts`

Represents the complete periodic report response for a date range with breakdowns by outlet,
product, and user dimensions.

**Properties:**

| Name       | Type                  | Description                                        |
| ---------- | --------------------- | -------------------------------------------------- |
| from       | string                | Start date of report period (ISO string)           |
| to         | string                | End date of report period (ISO string)             |
| user_id    | string                | Optional user ID to filter report to specific user |
| summary    | ReportSummary         | Aggregated financial summary                       |
| by_outlet  | ReportBreakdownItem[] | Breakdown of performance by outlet                 |
| by_product | ReportBreakdownItem[] | Breakdown of performance by product                |
| by_user    | ReportBreakdownItem[] | Breakdown of performance by user/salesperson       |
| fallback   | boolean               | Indicates if report used fallback data source      |

**Relationships:**

- has-one ReportSummary (Report contains one aggregated summary)
- has-many ReportBreakdownItem (Report contains breakdown by outlet dimension)
- has-many ReportBreakdownItem (Report contains breakdown by product dimension)
- has-many ReportBreakdownItem (Report contains breakdown by user dimension)

## Requirements

### Requirement: DashboardColorValidation

The system SHALL validate DashboardColor according to these rules:

- Must be one of: red, yellow, green, none

#### Scenario: ValidDashboardColorAccepted

- **GIVEN** A valid DashboardColor object with all required fields
- **WHEN** The object is validated
- **THEN** Validation passes with no errors

### Requirement: DashboardSummaryValidation

The system SHALL validate DashboardSummary according to these rules:

- total_outlets must be a non-negative integer
- total_bottles_in_market must be a non-negative integer
- urgent_count must be a non-negative integer
- urgent_count must be less than or equal to total_outlets

#### Scenario: LoadDashboardSummary

- **GIVEN** Dashboard data is requested
- **WHEN** /api/dashboard endpoint is called
- **THEN** Summary contains total outlets, bottles in market, and urgent count
- **AND** Dashboard items list is populated

### Requirement: DashboardItemValidation

The system SHALL validate DashboardItem according to these rules:

- latitude must be a valid geographic coordinate (-90 to 90)
- longitude must be a valid geographic coordinate (-180 to 180)
- max_age_hours must be non-negative
- open_cycles_count must be a non-negative integer
- total_qty_dropped must be a non-negative integer

#### Scenario: DetermineOutletColorStatus

- **GIVEN** Outlet has inventory and operational data
- **WHEN** Dashboard report is generated
- **THEN** Dashboard item displays with appropriate traffic-light color
- **AND** color is 'red' when max_age_hours exceeds threshold

#### Scenario: DisplayOutletInDashboard

- **GIVEN** Outlet exists in system
- **WHEN** User views dashboard
- **THEN** Dashboard item shows location, metrics, and visual status indicator
- **AND** photo_key may be null if no photo uploaded

### Requirement: DashboardReportValidation

The system SHALL validate DashboardReport according to these rules:

- items array must not be null
- summary must contain all required aggregated fields

#### Scenario: LoadCompleteDashboard

- **GIVEN** User requests dashboard view
- **WHEN** /api/dashboard endpoint returns successfully
- **THEN** Dashboard report contains summary and all outlet items
- **AND** items array length equals total_outlets in summary

### Requirement: ReportBreakdownItemValidation

The system SHALL validate ReportBreakdownItem according to these rules:

- qty_sold must be non-negative
- amount_collected must be non-negative
- hpp_used must be non-negative
- margin should equal amount_collected minus hpp_used
- waste must be non-negative

#### Scenario: CalculateBreakdownItemMargin

- **GIVEN** Sales and cost data exists for period
- **WHEN** Periodic report is generated
- **THEN** ReportBreakdownItem shows computed margin
- **AND** margin equals amount_collected minus hpp_used

### Requirement: ReportSummaryValidation

The system SHALL validate ReportSummary according to these rules:

- total_revenue must be non-negative
- total_hpp_used must be non-negative
- total_margin should equal total_revenue minus total_hpp_used
- total_waste must be non-negative
- visit_count must be non-negative integer
- override_count must be non-negative integer

#### Scenario: GenerateReportSummary

- **GIVEN** Periodic report data is aggregated
- **WHEN** Report generation completes
- **THEN** ReportSummary contains all financial aggregates
- **AND** total_margin should equal total_revenue minus total_hpp_used

### Requirement: ReportResponseValidation

The system SHALL validate ReportResponse according to these rules:

- from must be a valid date string
- to must be a valid date string
- to date must be after or equal to from date
- user_id must be a valid identifier when provided
- by_outlet array must not be null
- by_product array must not be null
- by_user array must not be null
- summary totals should equal sum of corresponding breakdown items across dimensions

#### Scenario: GeneratePeriodicReport

- **GIVEN** Date range is specified and data exists
- **WHEN** Report endpoint is called with from/to parameters
- **THEN** ReportResponse contains summary and all dimensional breakdowns
- **AND** by_outlet, by_product, by_user arrays contain ReportBreakdownItem structures

#### Scenario: UseFallbackReportData

- **GIVEN** Primary data source is unavailable
- **WHEN** Report generation uses secondary data source
- **THEN** ReportResponse is generated with fallback flag set to true
- **AND** fallback flag indicates data quality

### Requirement: GenerateReport

The system SHALL generates a comprehensive report aggregating visit submissions and consignment cycle data within a specified date range, optionally filtered by user. the report shall include summary metrics (total revenue, hpp used, margin, waste, visit count, override count) and breakdowns by outlet, product, and user.

#### Scenario: GenerateReportForDateRangeWithData

- **GIVEN** Committed visit submissions and consignment cycles exist within the requested date range
- **WHEN** generateReport is called with valid from and to dates
- **THEN** Returns report with aggregated summary metrics and breakdowns by outlet, product, and user
- **AND** Summary aggregates committed visit submissions within date range
- **AND** Financials exclude voided consignment cycles

#### Scenario: GenerateReportFilteredByUser

- **GIVEN** Multiple users have submitted visits in the date range
- **WHEN** generateReport is called with user_id parameter
- **THEN** Returns report containing only data for the specified user
- **AND** Visit conditions include user_id filter
- **AND** Cycle aggregation joins through visit_submissions to filter by user

#### Scenario: GenerateReportWithDefaultDates

- **GIVEN** No date parameters provided in request
- **WHEN** generateReport is called without from/to parameters
- **THEN** Returns report for current date
- **AND** from parameter defaults to current date
- **AND** to parameter defaults to current date

#### Scenario: RejectInvalidDateFormat

<!-- openlore-test: tags=regression (auto) -->

- **GIVEN** Invalid date format provided
- **WHEN** generateReport is called with malformed date string
- **THEN** Throws ValidationError
- **AND** ValidationError is thrown with message 'Format tanggal tidak valid (YYYY-MM-DD)'

#### Scenario: RejectInvalidDateValue

<!-- openlore-test: tags=regression (auto) -->

- **GIVEN** Date string in correct format but invalid date (e.g., 2023-02-30)
- **WHEN** generateReport is called with non-existent date
- **THEN** Throws ValidationError
- **AND** ValidationError is thrown with message 'Tanggal tidak valid'

#### Scenario: ExcludeVoidedCyclesFromFinancials

- **GIVEN** Consignment cycles with various statuses exist
- **WHEN** generateReport aggregates cycle data
- **THEN** Report financial metrics exclude any voided consignment cycles
- **AND** Margin calculated as amount_collected - hpp_used for each breakdown item
- **AND** Voided cycles excluded from all financial aggregations

#### Scenario: ExcludeDeletedOutletsFromBreakdown

- **GIVEN** Some outlets have been soft-deleted
- **WHEN** generateReport builds outlet breakdown
- **THEN** by_outlet breakdown does not include deleted outlets
- **AND** Deleted outlets excluded via isNull(outlets.deleted_at) condition
